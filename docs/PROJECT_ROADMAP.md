# 项目统一路线图

## 1. 项目目标

首个 MVP 跑通以下完整闭环：

```text
用户注册/登录
  → 在任务大厅领取任务，或由系统自动加入成长任务
  → 提交成果并审核，或由系统自动核验站内行为
  → 发放积分
  → 商城兑换或购买
  → 支付/扣积分
  → 发货/确认收货
  → 售后与对账
```

首发平台确定为微信小程序和通用 H5。H5 可从微信公众号进入，也允许在微信外的浏览器打开；两端共享同一套业务 API、用户体系和订单数据。Android 和 iOS 在核心业务稳定后进入正式发布。管理后台与 API 从第一期开始建设。

## 2. MVP 范围控制

### 必须包含

- 手机号或微信登录、账号绑定和注销
- 用户、角色与后台权限
- 平台管理员在管理后台或用户端任务发布中心发布、任务大厅、主动领取/系统自动加入、提交/自动核验、审核和撤回规则
- 任务模板中心、批次数据项、领取验证双状态机、按步骤审核和周期成长任务
- 积分账户、冻结积分与不可篡改流水
- 用户余额钱包、余额奖励和不可篡改流水
- 余额商城支付、提现申请、冻结、渠道转账和财务对账
- 商品分类、SPU、SKU、库存和上下架
- 购物车、地址、订单、取消和超时关闭
- 纯积分兑换、纯现金支付、现金加积分三种购买方式
- 每个 SKU 可同时开放三种购买方式，后台也可只启用其中一种或两种
- 微信小程序、微信内 H5 和微信外 H5 的现金支付适配
- 客户端能力检测与降级：H5 支付不可用时保留浏览、手机号登录、购物车和余额足额支付
- 现金运费、积分有效期、优惠券和部分退款
- 发货、确认收货、退款/退积分和基础售后
- 站内消息、操作日志和基础数据看板
- 后台参数配置中心：开关、选项、数值、有效期、版本、审核和回滚
- 每日签到、完善资料、推荐新人等成长行为
- 基础论坛帖子、评论、内容审核、举报和违规处理
- 隐私协议、用户协议、退款规则和客服入口

### MVP 暂缓

- 多商户入驻和结算
- 分销、拼团、秒杀和复杂优惠叠加
- 社交动态、即时聊天和直播
- 智能推荐和复杂会员等级
- 校园跑腿、快递代取、代买代送、骑手角色、配送调度、位置轨迹和线下到场履约
- 微服务、跨地域多活和数据仓库

完整的 P0、明确不做、延后预留和冻结后变更流程见 [`product/MVP_SCOPE.md`](product/MVP_SCOPE.md)。隐私保留基线见 [`security/PRIVACY_DATA_RETENTION.md`](security/PRIVACY_DATA_RETENTION.md)，真实资质与第三方账号准备状态见 [`security/COMPLIANCE_READINESS.md`](security/COMPLIANCE_READINESS.md)。

任何新增需求先记录变更原因、收益、成本和对发布日期的影响，再决定是否进入当前版本。

## 3. 端到端阶段

### G0：项目基线

工作内容：

- 明确目标用户、核心价值、首发平台和商业模式。
- 确认积分是否具有有效期、能否退款、能否转让。
- 商品购买方式已确定为纯积分、纯现金、现金加积分三种形式。
- 混合支付 MVP 采用后台为 SKU 配置固定现金额和固定积分额，不允许用户自由调整抵扣比例。
- 运费只使用现金支付。
- 后台设置全局积分有效期，并允许签到、发帖、评论、完善资料、推荐新人等积分来源覆盖默认有效期。
- 退款积分从退款入账时重新计算有效期，并沿用原消费积分对应来源的当前有效期规则。
- 支持按数量部分退款、整项退款和整单退款。
- 每笔订单最多使用一张优惠券；优惠券可以抵扣现金、积分或同时抵扣两者。
- 整单取消或整单退款后返还优惠券；部分退款和整项退款但订单仍有保留商品时不返券。
- 退货原因决定责任方；买家原因通常由买家承担退货运费，卖家或物流责任不让用户最终承担，争议场景由客服审核。
- 已完成交付并实际退货时原订单运费不退；未发货或始终未收到货且无需退货的整单退款可以退回。
- 微信小程序、微信内 H5 和微信外 H5 使用相同的商品价格。
- 确认任务成果包含的文本、图片、视频和文件类型。
- 建立 MVP 范围、非目标、负责人和计划日期。

交付物：产品简报、范围清单、成功指标、风险清单。

验收门槛：所有影响数据模型和支付资质的问题都有明确结论。当前仍需确认各积分来源的具体有效期天数、积分奖励数额及上限、退回优惠券有效期和部分退款服务费规则。

### G1：需求与业务规则

工作内容：

- 编写用户故事和可验证的验收标准。
- 定义用户、任务、积分、库存、订单、支付和退款状态机。
- 定义并发领取、重复提交、审核撤销、库存不足等异常流程。
- 定义消息通知时机、客服流程、内容审核和申诉机制。
- 确认隐私、账号注销、数据保留、图片版权和商品售后规则。

交付物：需求基线、状态机、术语表、业务规则、页面清单。

验收门槛：产品、设计、前端和后端对每个状态及异常路径理解一致。

### G2：原型与视觉设计

按照 `design/DESIGN_PLAN.md` 执行：

- 信息架构和低保真原型
- 设计 Token、组件和图标体系
- 用户端与管理后台高保真页面
- 加载、空、错误、无权限、禁用和成功状态
- 多端适配及真机走查

验收门槛：当前迭代页面通过设计评审，下一迭代原型已经准备。

已确认的视觉、图标与原型验收基线见 [`../design/UI_DESIGN_SYSTEM_BASELINE.md`](../design/UI_DESIGN_SYSTEM_BASELINE.md)，后台信息架构见 [`product/ADMIN_INFORMATION_ARCHITECTURE.md`](product/ADMIN_INFORMATION_ARCHITECTURE.md)。

### G3：技术基线与开发环境

工作内容：

- 安装并锁定 Node.js、PHP、Composer 和包管理器版本。
- 初始化 uni-app、React、Laravel 可运行项目。
- 使用 Docker Compose 启动 PostgreSQL、Redis 和本地对象存储替代服务。
- 建立开发、测试、预发布、生产四套配置。
- 建立代码格式化、静态检查、单元测试和 CI。
- 确定日志、错误码、请求 ID、时区、金额和积分数值规则。

验收门槛：新环境可以按照 README 一次启动；三端健康检查通过；密钥不进入仓库。

工程与环境约束见 [`architecture/TECHNICAL_BASELINE.md`](architecture/TECHNICAL_BASELINE.md)，性能、安全、恢复和兼容目标见 [`quality/NON_FUNCTIONAL_REQUIREMENTS.md`](quality/NON_FUNCTIONAL_REQUIREMENTS.md)。

### G4：数据模型与 API 契约

工作内容：

- 完成 ER 图、索引、唯一约束、外键和数据保留策略。
- 明确金额使用人民币分整数，积分使用整数，时间统一存储规则。
- SKU 分别保存现金价、积分价和混合支付所需的现金及积分，不使用浮点数计算。
- 完成 OpenAPI 契约、分页、错误码和幂等键规范。
- 建立数据库迁移、回滚、种子数据和测试数据工厂。
- 对登录、任务审核、积分、库存、订单和支付做威胁建模。

验收门槛：迁移可重复执行和回滚；契约可生成客户端类型；关键状态转换有测试案例。

### G5：迭代一——认证与基础能力

- 登录、刷新 Token、退出、微信小程序与公众号身份绑定
- 使用统一用户身份关联小程序 OpenID、公众号 OpenID；具备条件时通过 UnionID 合并身份
- 微信外 H5 支持手机号等不依赖微信网页授权的登录方式
- 用户资料、地址、设备、隐私授权和账号注销
- 管理后台登录、RBAC、菜单权限和操作审计
- 超级管理员、运营、任务审核、社区审核、客服、仓储、财务和审计角色
- 高风险退款、积分调整和批量发券的二次审核
- 后台配置中心、配置版本、规则快照和缓存刷新
- 文件上传、通知基础设施和全局异常处理

验收门槛：用户端和后台权限隔离有效；上传文件经过类型、大小和访问权限检查。

### G6：迭代二——任务与积分

- 任务创建、发布、领取、提交、审核和驳回
- 任务模板、模板版本、从模板创建草稿和批次数据导入
- 批次数据项领取时原子分配、使用追踪和结果导出
- 用户任务状态与审核状态分离，支持审核分派、驳回补交和申诉复核
- 名额、截止时间、重复领取和提交限制
- 积分账户、冻结、发放、扣减、撤销和流水
- 任务积分、优惠券和余额奖励组合
- 用户钱包、余额发放、冻结、消费、退款和人工调整流水
- 用户资产后台操作、提现审核和提现渠道适配
- 积分规则引擎：来源、奖励数额、有效期、每日/总次数上限和启用状态
- 积分批次：按来源记录发放、剩余和过期时间，消费时优先使用最早到期批次
- 签到、社区发帖/评论、完善资料和推荐新人事件接入
- 每日、每周、每月和里程碑周期任务的进度、重置与幂等发奖
- 审核通知、申诉入口和后台审核工作台

验收门槛：重复事件不会重复发积分；并发领取不会突破名额；每次余额变化都有对应流水和积分批次；过期及退款重新计时可验证。

### G7：迭代三——商城与订单

- 分类、商品、SKU、价格和库存
- 购物车、收货地址、确认订单和订单快照
- 库存预占、释放、扣减和库存流水
- 纯积分、纯现金、现金加积分下单
- 每个 SKU 独立配置三种购买方式的启用状态和价格
- 下单时保存 SKU 现金与积分价格快照
- 订单取消、超时关闭、积分解冻和确认收货
- 运费始终计入现金应付金额

验收门槛：压力测试下无库存负数；商品修改不影响历史订单；取消订单正确返还库存和积分。

### G8：迭代四——支付、履约与售后

- 微信小程序、微信内 H5 与微信外 H5 的支付渠道和支付单
- 回调验签、幂等、查询补偿和异常订单处理
- 发货、物流、现金退款、退积分和售后工单
- 混合支付订单分别记录现金和积分的支付、退款结果
- 支持按数量部分退款、整项退款和整单退款，并保存每次退款明细
- 退款积分从退款入账时间重新计算有效期
- 优惠券优惠按订单项分摊，退款不得超过订单项实际支付金额与积分
- 整单退款完成后返券；原运费和退货运费按售后原因及责任规则处理
- 日对账、差异订单、人工处理和审计记录

验收门槛：重复回调不会重复入账；支付成功但回调丢失可自动补偿；纯积分、纯现金和混合支付均可独立对账并正确退款。

### G9：质量、安全和发布准备

- 单元、接口、集成、E2E、并发和真机测试
- 权限越权、注入、XSS、文件上传、重放和限流测试
- 性能基线、慢查询、包体积和图片资源检查
- 隐私清单、第三方 SDK、权限用途和应用商店材料
- 数据备份恢复、数据库迁移、灰度、回滚和故障演练

验收门槛：阻断和严重缺陷为零；备份恢复及回滚演练通过；发布清单全部签字确认。

测试矩阵见 [`quality/ACCEPTANCE_TEST_MATRIX.md`](quality/ACCEPTANCE_TEST_MATRIX.md)，灰度、止损和运营机制见 [`releases/RELEASE_AND_OPERATIONS_STRATEGY.md`](releases/RELEASE_AND_OPERATIONS_STRATEGY.md)。

### G10：上线与运营闭环

- 先内部测试，再小范围灰度，最后逐步放量。
- 监控 API 可用性、错误率、延迟、队列、数据库和支付回调。
- 监控注册、任务领取、提交、审核、积分使用、下单和支付转化。
- 每日执行支付、退款、积分和库存对账。
- 建立客服、内容审核、异常补偿和事故响应流程。
- 上线后复盘真实数据，再决定 App 和下一阶段功能。

验收门槛：核心指标和告警可见；值班及故障联系人明确；关键账务每日可闭环。

## 4. 推荐迭代节奏

每个迭代建议两周：

1. 第一天确认目标、范围和验收标准。
2. 设计领先开发一个迭代。
3. 每日同步阻塞、风险和接口变更。
4. 中期完成接口联调和风险复查。
5. 迭代结束演示真实业务闭环，不只展示静态页面。
6. 演示后完成回归、复盘和下一迭代调整。

## 5. 统一就绪与完成定义

### 开始开发前必须满足

- 需求和非目标明确。
- 原型及页面状态已评审。
- API 契约和数据权限已确认。
- 验收案例、异常路径和测试数据已准备。
- 不存在未决的支付、隐私或资质问题。

### 功能完成必须满足

- 代码、迁移、接口文档和测试同步完成。
- 正常、异常、并发和权限路径通过。
- 日志、指标和审计信息可定位问题。
- 设计走查和目标平台真机验证通过。
- 无高等级安全问题，具备回滚或关闭开关。
