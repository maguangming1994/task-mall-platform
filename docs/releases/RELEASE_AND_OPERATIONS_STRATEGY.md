# 灰度发布、回滚与运营保障策略

## 1. 发布顺序

默认采用：开发自测 → 测试环境 → 预发布演练 → 内部账号 → 白名单用户 → 小比例灰度 → 分批放量 → 全量。每一阶段都有观察窗口和继续/停止负责人，不能只按时间自动放量。

## 2. 变更与功能开关

- 新页面、入口、活动和非账务流程优先受服务端功能开关保护。
- 数据库采用先扩后缩的兼容迁移：先增加兼容结构，再切换读写，稳定后才移除旧结构。
- 功能开关不能回退已发生的支付、奖励、库存和退款事实；账务变更必须有前向修复和对账方案。
- 代码、配置、数据库、客户端、活动任务和第三方渠道分别编写回滚/停止方案。

## 3. 发布检查

- 固定版本范围、提交号、迁移、配置差异、负责人和回滚点。
- CI、验收、安全、设计走查、生产资质、密钥、回调域名和监控全部通过。
- 发布前创建可恢复备份并验证最近一次恢复演练有效。
- 灰度后执行登录、任务、奖励、三种购买、两种现金支付、退款和对账冒烟。

## 4. 监控与对账

- 监控错误率、p95、数据库、Redis、队列、对象存储、外部调用和支付回调。
- 每日自动对账支付、退款、余额、积分、优惠券、预算、订单和库存；差异进入人工队列。
- 高风险任务2小时、普通投诉24小时等业务 SLA 进入运营看板并逾期升级。
- 放量期间重点观察注册、任务领取/完成、发奖、下单、支付、退款和客服量变化。

## 5. 回滚与止损

触发条件包括核心流程不可用、越权/数据泄露、重复扣款/发奖/退款、库存或账务不一致、错误率/延迟/队列持续超阈值。

止损优先顺序：关闭入口或活动 → 停止新写入/领取 → 隔离消费者或外部渠道 → 保全日志和账务 → 前向修复或应用回滚。禁止在未验证备份和影响范围时执行破坏性数据库回滚。

## 6. 事故与客服

- 事故分为 P0—P3，分别定义响应、升级、业务止损、用户通知、补偿和复盘要求。
- 每个生产告警有值班人、替补和业务负责人；重大事故保留时间线、决定、数据修复和用户影响清单。
- 客服明确工作时间、售后/投诉 SLA、升级人和标准话术；客服不能直接修改支付或资产流水。
- 发布前准备小程序审核、隐私弹窗、功能说明、截图、版本公告和客服知识库。
