# 部署、监控、备份、回滚与灰度手册

## 发布前

1. 准备 `infra/.env.production`，不得提交仓库；所有占位值必须替换为独立随机密钥。
2. 执行 `production:readiness --strict`、`system:consistency-audit --strict` 和 `scripts/prepare-release.ps1`。后者运行完整 UAT，并登记提交、三端制品和部署配置的不可变摘要。
3. 使用 `docker compose -f infra/compose.production.yaml config` 校验配置，再构建 API 与 Web 镜像；镜像必须使用版本号和摘要，不得使用浮动 `latest` 作为回滚依据。
4. 先执行数据库备份并完成隔离恢复演练。备份密码只能通过环境变量传入，备份清单包含文件大小与 SHA-256。

## 灰度发布

1. 外部负载均衡器先把 1% 流量切向新版本，再登记 `release:transition <版本> canary --percentage=1`。
2. 每阶段至少观察 readiness、5xx、p95、队列积压、支付成功率、退款失败、账务差异和业务一致性；建议阶段为 1% → 5% → 20% → 50% → 100%。
3. 功能开关按稳定主体摘要分桶，同一用户不会随机漂移；可叠加端类型和最多 100 个主体白名单。灰度比例只允许递增，停用必须回到 0%，全量必须为 100%。
4. 生产全量发布前再次执行生产就绪门禁；未通过时服务端拒绝登记全量完成。

## 监控与告警

- `/api/v1/internal/metrics` 仅接受至少 32 位的 `X-Monitoring-Token`，错误令牌返回 404；指标不含用户标识、路径参数、凭据或异常文本。
- Prometheus 指标覆盖进程、依赖就绪、业务一致性、失败/等待队列、失败消息和待处理退款。API 响应同时提供 `Server-Timing`；超过阈值的请求仅记录路由模板、请求 ID、状态码和耗时。
- P0：支付错误、资金/积分错账、数据泄露或核心不可用；立即停止灰度并回滚。P1：主要链路错误率持续升高或队列严重积压；冻结发布并评估回滚。

## 回滚

1. 回滚流量和应用镜像，不自动回滚数据库迁移；所有迁移按向前兼容、先扩展后收缩设计。
2. 登记 `release:transition <版本> rollback`，必须附事故/验收证据 SHA-256 和明确原因；事件只追加，不可删除。
3. 回滚后运行 readiness、一致性审计、支付主动查询、退款补偿重试、通知重试和隐私删除重放。
4. 只有指标恢复、账务一致且 P0/P1 止损完成后才重新开放流量。

## 备份恢复

- 每日至少一次 PostgreSQL 自定义格式备份，资金和订单高峰前额外备份；生产保留策略由合规与存储容量共同确认。
- 每月至少做一次 `restore-drill.ps1` 隔离恢复；脚本只会创建并删除带 `task_mall_restore_drill_` 前缀的临时数据库。
- 恢复旧备份后必须先迁移、再执行 `privacy:replay-deletions` 和一致性审计，避免已注销数据复活。
