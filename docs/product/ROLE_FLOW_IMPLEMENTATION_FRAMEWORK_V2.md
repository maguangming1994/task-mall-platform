# 任务商城角色与流程实施框架 V2

更新时间：2026-08-13  
适用范围：微信小程序、微信公众号 H5、通用 H5、PC 管理后台、Laravel API、在线 UI 总览

可视化评审入口：[角色流程图 V3](../../角色流程截图/角色流程图-V3.md)；XMind 入口：[任务商城系统-项目总览](../../xmind/任务商城系统-项目总览.xmind)。

## 1. 产品边界

平台首发仍是“平台自营任务 + 平台自营商城 + 校园社区”。在线 UI 总览是设计和验收入口，不是独立业务源；正式页面、接口、权限和状态以本文件及服务端状态机为准。

校园有偿求助首期按“社区需求内容”实现：普通用户可以创建需求草稿、提交审核、修改被驳回内容和关闭需求；平台审核后公开展示。首期不开放用户悬赏资金托管、抢单、骑手、位置轨迹、线下履约结算。以后若恢复这些能力，必须新建资金、履约、争议和风控状态机，不能复用平台任务奖励账本。

## 2. 角色框架

| 角色 | 使用端 | 核心目标 | 可执行动作 | 明确禁止 |
|---|---|---|---|---|
| 游客 | 移动端 | 了解平台 | 浏览公开任务、商品、社区和协议 | 领取、下单、互动、查看个人数据 |
| 普通用户 | 移动端 | 完成任务、兑换购物、参与社区 | 领取/提交/补交/申诉任务；购物和售后；发帖、评论、活动与有偿求助草稿；管理资产与隐私 | 发布平台悬赏、操作他人数据、后台管理 |
| 平台管理员 | 后台 + 限权移动发布端 | 经营平台任务 | 创建、编辑、提审、发布和管理本人任务 | 审核自己触发的高风险发布、处理财务资产 |
| 运营管理员 | 后台 | 经营内容和商品 | 任务运营、商品运营、首页装修、公告与消息 | 财务终审、权限配置 |
| 任务审核员 | 后台 | 审核任务材料 | 接单、逐步骤审核、释放/转派、任务申诉处理 | 修改任务奖励、审核自己的发布申请 |
| 社区审核员 | 后台 | 社区安全与质量 | 帖子/评论/活动/需求审核、举报和申诉 | 修改用户资产、任务审核 |
| 客服人员 | 后台 | 解决用户问题 | 工单、售后初审、脱敏查询、协商记录 | 直接改账、改库存、查看无关敏感数据 |
| 仓储人员 | 后台 | 标准商品履约 | 库存流水、发货、收货确认、物流凭证 | 资金退款、任务与社区审核 |
| 财务人员 | 后台 | 资金和资产安全 | 提现、退款复核、预算池、对账、人工资产调整审核 | 修改业务内容、审核本人申请 |
| 审计人员 | 后台 | 追踪风险 | 脱敏只读、审计日志和报表 | 任何业务写操作 |
| 超级管理员 | 后台 | 系统治理 | 角色权限、配置审批、应急处置 | 绕过审计、删除资产事实流水 |

## 3. 主流程与状态机

### 3.1 登录、协议与账号

游客打开页面 → 勾选当前版本用户协议与隐私政策 → 微信或手机号登录 → 合并身份 → 补全资料/绑定手机号 → 进入业务。协议升级后按后台配置重新征得同意；拒绝时仅保留退出、查看协议和数据权利入口。

### 3.2 平台任务闭环

后台任务草稿 → 内容/步骤/奖励预算校验 → 高风险发布复核 → 排期/发布 → 用户领取并预留全部奖励 → 分步骤填写和上传 → 提交审核 → 审核员占用审核单 → 逐步骤通过或驳回 → 用户仅补交失败步骤 → 全部通过 → 奖励组件独立发放 → 到账/失败重试 → 必要时申诉和异人复核。

任务同时维护三组状态：

| 状态维度 | 标准状态 |
|---|---|
| 执行状态 | 已预留、进行中、可提交、审核中、待补交、申诉中、已完成、已放弃、已过期、已终止 |
| 审核状态 | 未分配、排队中、审核中、待补交、已通过、已驳回、已作废 |
| 奖励状态 | 未开始、已预留、发放中、部分到账、全部到账、发放失败待重试 |

前端按钮、可编辑步骤和下一步提示必须读取服务端 `workflow`，不得只根据旧的 `status` 字段推断。

### 3.3 商城闭环

商品/分类/规格/SKU/主图与轮播 → 三种购买方式配置 → 购物车或立即购买 → 地址和配送方式 → 优惠券 → 余额全额或微信全额承担现金应付 → 创建订单和库存预占 → 支付 → 标准物流/无需物流/虚拟交付 → 确认收货 → 退款、退货或同 SKU 换货 → 资产与库存逆向处理 → 对账。

固定规则：运费只用现金；同一 SKU 可开放纯现金、纯积分、现金+积分；余额不能与微信现金组合；各端价格一致；退货原运费默认不退；退货运费责任由原因配置决定。

### 3.4 社区、活动与校园需求

帖子/活动/有偿求助草稿 → 本地保存 → 提交审核 → 通过后公开 → 点赞、评论、举报 → 内容处置/奖励撤销 → 申诉复核。校园需求需要校园范围、需求类型、正文、公开信息、仅接单后可见信息、图片、预算展示和协议确认；首期“预算”仅作需求描述，不产生平台托管或可提现资产。

### 3.5 客服、隐私与后台治理

用户工单/投诉 → 客服受理 → 分类转派 → 处理与补充材料 → 用户确认/自动关闭。敏感数据默认脱敏，查看原文、导出、人工调账、权限修改和高风险配置发布必须留下原因、请求 ID、操作前后快照和审批记录。

## 5. 在线 UI 总览采用规则

1. “任务、商城、社区、账号、售后、后台工作台”页面作为正式实现蓝图，并标注真实路由和实现状态。
2. “校园跑腿、多商户门店、骑手调度、位置轨迹”只保留为下一版本研究稿，不进入首发导航和验收。
3. 高保真稿中的数字、按钮和状态必须能映射到真实接口字段；没有接口的交互必须标记“概念/待开发”，不能伪装成已完成。
4. 同一业务在小程序、微信 H5、通用 H5 共享信息架构和价格，只允许系统导航、支付能力和分享方式存在端差异。

## 6. 实施顺序

1. 任务履约闭环：服务端工作流提示、失败步骤补交、审核工作台和奖励状态。
2. 商城规格到售后闭环：商品媒体/SKU、结算、支付能力、物流和部分退款。
3. 社区需求闭环：需求类型、公开/私密字段、审核和关闭，不启用资金托管。
4. 账号、资产、客服、隐私和通知入口统一。
5. 更新在线 UI 总览的实现状态与真实路由，完成 H5、小程序和后台构建验收。

## 7. 首批验收标准

- 用户被驳回后只看到并只能编辑失败步骤，通过步骤显示“已通过并沿用”。
- 用户端下一步按钮由服务端工作流返回，旧状态兼容但不作为唯一判断依据。
- 审核员接单后形成 30 分钟占用锁，可释放或转派；每一步都有中文结论与原因。
- 任一步驳回不发奖励；全部通过后各奖励组件独立到账，失败组件可重试且不重复发放。
- 在线 UI 总览、移动端和后台对同一状态使用一致中文名称。
