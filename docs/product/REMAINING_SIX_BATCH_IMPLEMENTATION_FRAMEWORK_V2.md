# 剩余六篇整体实现框架 V2

> 日期：2026-08-13。本文是在线 UI 总览、uni-app 用户端、PHP API 与 PC 管理后台的统一开发交付基线。

## 总览

| 篇章 | 核心角色 | 闭环 | 当前实装重点 |
|---|---|---|---|
| 资产与财务 | 用户、财务、超级管理员 | 获得 → 冻结/消费 → 退款重算 → 提现 → 对账 | 积分来源有效期、FIFO、余额提现费率、失败解冻、中文下一步 |
| 社区与消息 | 学生、活动发起人、社区审核员 | 发布 → 审核 → 互动/组团 → 举报申诉 → 消息直达 | 帖子/评论/点赞/活动、通知偏好和内容深链 |
| 成长与邀请 | 学生、运营管理员 | 签到/任务/邀请 → 里程碑 → 奖励批次 | 每日签到幂等、连续天数、推荐首任务+首笔现金订单 |
| 账户与服务 | 用户、客服、隐私管理员、超级管理员 | 资料 → 协议 → 隐私请求/注销 → 工单沟通 | 角色权限、协议版本、数据副本、注销阻塞、工单下一步 |
| 运营与风控 | 运营、财务、审计、超级管理员 | 配置草稿 → 复核发布 → 监控 → 审计追溯 | 设置版本、上线就绪分组、敏感值不回显、异常重试 |
| 微信真机与发布 | 开发、测试、发布负责人 | 构建 → 开发者工具 → 真机 UAT → 体验版 → 审核发布 | 安全配置检查、设备矩阵、支付回调、回滚与密钥轮换 |

## 1. 资产与财务

- 积分不是单一余额：必须保留来源、获得时间、有效期、剩余量、退款重算及欠额。
- 余额支付与现金支付互斥；余额只能“不使用”或“全部使用”，不允许余额+现金混合。
- 提现费率默认千分之六但以后台当前版本为准；提交后冻结，拒绝/失败自动解冻，成功才扣除冻结余额。
- 用户端展示 `status_label + next_action`；财务端保留审核、打款、渠道查询、重试和对账证据。

## 2. 社区与消息

- 帖子和评论审核前不可公开；修改已发布帖子生成新版本，旧版继续服务直到新版通过。
- 活动状态为待审、招募中、已满、已开始、已结束、已关闭；发起人与参与人权限分离。
- 举报与申诉都保留理由、证据、处理人和审计记录。
- 消息中心按任务、资产、订单、售后、社区、系统分类；社区消息携带帖子或活动 ID，点击直达对应详情。

## 3. 成长、签到与邀请

- 每日签到一天一次，接口和奖励事件均幂等；断签后连续天数从 1 重新计算。
- 签到奖励数量与有效期分别读取后台积分配置；入账后在积分批次和流水可追溯。
- 推荐奖励必须同时完成“第一次任务”和“第一笔现金订单”，并受后台月度奖励上限约束。
- 周期成长任务与一次性任务共用奖励幂等机制，避免重复发奖。

## 4. 账户、角色、协议、隐私与客服

- 管理角色支持新增、编辑、禁用和权限配置；敏感权限与高风险设置发布必须审计。
- 前端首次使用对应业务前完成协议勾选，后台管理协议草稿、版本、生效时间和强制重签。
- 数据副本和注销均先返回资格与阻塞原因；注销执行冷静期和最终复核。
- 客服工单由服务端返回中文状态、下一步、可回复与可关闭能力，避免移动端自行猜测。

## 5. 运营、配置、审计与风险

- 首页、导航、图片、图标、公告、协议、积分、提现、任务和售后默认参数均由后台版本化配置。
- 高风险配置采用草稿与发布隔离，发布后记录操作者、差异、理由和时间。
- 上线检查按运行环境、安全、基础设施、微信、支付、短信、消息、存储、合规分组。
- 服务端只返回“是否就绪”和修复动作，永不返回真实密钥。

## 6. 微信真机与正式发布

- 本地联调、体验版与正式版使用不同的环境文件和域名策略。
- 真机覆盖微信登录、手机号、协议、签到、任务、支付、退款、社区、上传、通知和客服。
- 正式发布前执行 `scripts/check-wechat-readiness.ps1 -Strict`，任一前置条件失败即停止发布。
- 曾通过聊天、截图或不安全渠道出现过的密钥必须先轮换，不能直接用于生产。

## 验收标准

1. 每个状态都能解释“现在发生了什么、用户还能做什么、下一步是什么”。
2. 关键金额、积分、库存、名额和奖励操作幂等且可审计。
3. 移动端、管理端和在线 UI 总览使用相同中文状态和业务规则。
4. PHP 测试、uni-app 类型检查/H5/小程序构建、管理后台类型检查/构建全部通过。
