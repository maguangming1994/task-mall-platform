# 任务奖励预算、预留与结算规则

## 1. 基本原则

- 任务奖励只能使用平台统一预算池，发布者不能使用个人积分、优惠券或钱包余额作为任务预算。
- 积分、优惠券和余额预算分别核算；一种任务包含多种奖励时，每种奖励必须分别足额通过校验。
- 所有带奖励任务必须设置最大奖励次数；每日、每周和可重复任务同时设置单周期上限和活动总上限。
- 任务发布前锁定平台预算，用户参与时再从任务预算中预留个人奖励，审核或自动核验通过后转为已发放。
- 预算不足不能产生“完成任务但没有奖励”的用户任务记录。

## 2. 三类预算

| 奖励类型 | 平台预算单位 | 发布时锁定 |
|---|---|---|
| 积分 | 积分数量 | 单次积分 × 最大奖励次数 |
| 优惠券 | 指定模板的券数量 | 每次张数 × 最大奖励次数 |
| 余额 | 人民币分 | 单次余额金额 × 最大奖励次数，100%锁定现金预算 |

客户端只提交预算池和奖励次数上限，服务端根据任务奖励重新计算锁定值。客户端计算结果不能作为账务依据。

## 3. 发布预算校验

- 草稿和预览不实际锁定预算，但显示预计占用。
- 提交发布时锁定全部活动总预算；任一奖励预算不足时，整个任务发布失败，不允许只锁定部分奖励。
- 优惠券模板必须处于可发行状态，且模板总量减去其他活动已锁定数量后足够。
- 积分预算锁定的是平台发行额度，不等同于现金资产。
- 余额属于可支付、可提现的平台负债，必须绑定可用现金预算池并100%锁定。
- 单用户单次余额奖励超过 200 元继续走既有财务二审；任务余额总预算超过 5000 元也需要财务二审。两个门槛均由后台版本化配置。
- 当前实现中，命中任一门槛会保存任务版本、命中规则和阈值快照，并进入 `pending_approval`；申请人与复核人必须不同，批准后再次发布才按稳定预算池顺序加锁。
- 发布申请被驳回、撤销或草稿作废时，尚未生效的锁定幂等释放。

## 4. 用户奖励预留

- 用户主动领取或系统自动加入时，在同一事务中创建用户任务并预留该用户的全部奖励组件。
- 任一奖励组件无法预留时，不创建用户任务，也不占用领取名额。
- `task_claim_id + reward_type + reward_sequence` 唯一，重复请求不能重复占用预算。
- 自动加入任务只有成功预留奖励后才向用户展示为已加入。
- 已提交、审核中、申诉中和奖励重试中的用户始终保留预算，后台不得强制挪用。

## 5. 预算结算和释放

| 用户任务结果 | 预算动作 |
|---|---|
| 审核或自动核验通过 | 预留转已发放 |
| 用户在允许阶段取消 | 释放个人预留 |
| 未提交且到期 | 释放个人预留 |
| 最终驳回且申诉期结束/申诉驳回 | 释放个人预留 |
| 奖励投递失败 | 保持预留，进入重试或人工补偿 |
| 任务暂停 | 已参与用户继续保留，停止新预留 |
| 任务关闭/到期 | 等待所有审核、申诉和奖励重试结清后释放剩余预算 |

任务预算耗尽时停止新领取和系统自动加入，已预留用户仍可提交、审核、申诉和正常发奖。

## 6. 调整与追回

- 后台可以追加任务预算；追加余额预算超过总预算二审门槛时需要财务审批。
- 只能减少尚未分配的预算，调整后总预算不得低于已预留加已发放值。
- 积分、优惠券或余额只有实际追回成功后才能形成预算回收流水；积分欠额、余额待追偿和已经使用的优惠券不能视为已回收。
- 回收预算默认回到原平台预算池，不自动增加任务可发名额；需要继续发放时另行追加任务预算和奖励次数。
- 人工调整必须填写原因，并根据金额、积分和操作类型触发既有二次审核。

## 7. 流水与对账

预算锁定、追加、预留、发放、释放、追回和人工调整均生成不可删除流水，至少记录：

- 预算池、任务、用户任务和奖励组件
- 资产类型、变动数量、变动前后余额
- 业务事件、幂等键、操作人、审批记录
- 来源渠道、发生时间、请求 ID

每日分别对账平台预算池、任务预算、用户预留、奖励投递和用户资产流水。任一层级不一致时停止相关任务新领取并告警，不能通过覆盖汇总字段消除差异。
