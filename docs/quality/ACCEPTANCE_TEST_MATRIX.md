# 测试矩阵与逐项验收基线

## 1. 需求追踪

每条 P0 需求在开发开始前必须关联：需求 ID、业务规则、原型页面、OpenAPI 操作、数据表/迁移、正常/异常/权限/并发测试、负责人和验收人。没有可验证场景的需求不得标记开发就绪。

## 2. 测试层级

- 单元：金额/积分分摊、期限、资格、状态转换和规则函数。
- 接口：参数、权限、幂等、分页、错误码、版本冲突和数据范围。
- 集成：PostgreSQL、Redis、队列、对象存储、微信/支付/物流适配器。
- E2E：登录—任务—奖励—商城—支付—履约—售后闭环。
- 并发：任务名额、预算预留、库存、优惠券、钱包、支付回调和累计退款。
- 安全/隐私：越权、输入、上传、限流、敏感日志、隐私请求和到期删除。
- 性能/恢复：目标负载、队列积压、备份恢复、第三方超时与补偿。
- 真机/视觉：小程序、微信内/外 H5、管理后台及全部页面状态。

## 3. 核心业务矩阵

- 购买方式覆盖纯积分、纯现金、现金+积分；现金来源覆盖余额全额和微信全额且互斥。
- 每种购买覆盖优惠券可用/不可用、运费、库存不足、超时、重复请求和价格变化。
- 售后覆盖未发货、已发货、无需物流、虚拟商品、部分数量、整项、整单、多次退款和运费补偿。
- 任务覆盖三种参与方式、一次/日/周/重复周期、资格、名额、预算、取消、过期、提交、审核、申诉、冻结和补位。
- 社区覆盖发布、审核、举报、下架、奖励撤销、欠额和申诉。

## 4. 强制不变量

- 当前任务占位 + 成功奖励数不超过总奖励次数。
- 库存、积分、余额、预算和优惠券不得出现无来源负数或重复流水。
- 累计退款数量、现金和积分不超过剩余可退数量与实际支付。
- 余额与微信不组合支付同一订单现金应付；运费不使用积分。
- 资产流水与账户汇总、支付渠道、订单及库存对账一致率 100%。

## 5. 发布门槛

- P0/P1 缺陷为零，核心 E2E 全部通过。
- 支付使用沙箱和受控生产小额验证；重复、延迟、乱序和丢失回调可补偿。
- 无超卖、重复发奖、重复退款、权限越权和账务差异。
- 数据库迁移/回滚、备份恢复、监控告警和功能关闭演练通过。
- 产品、设计、开发、测试、运营、财务和安全按职责签字；法务仅对其正式材料与合规范围签字。
